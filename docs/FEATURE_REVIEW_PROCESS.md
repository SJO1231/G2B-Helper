# 기능별 독립 HTML 검토 공정

기준일: 2026-09-29. 출처: 사용자의 최신 지시 「각 기능별로 구분해서 html 형태로 개별로 구현」「구분해서 확인하고 취합」「공정별 필요한 모델과 등급」「의견은 별도」「피드백 전 수정 제한」.

## 사용자 지시와 현재 상태

- 기능을 독립 HTML/JS/CSS로 구현하고 하나씩 확인한 뒤 조합한다. 한 번에 전체를 바꾸지 않는다.
- 공정마다 추천 모델·추론 등급, 별도 의견, 검증 결과를 제시한다.
- 검토를 요청한 버전은 사용자 피드백 전까지 변경하지 않는다. 침묵·테스트 통과·다른 기능에 관한 답변을 승인으로 간주하지 않는다.
- 현재 `prototypes/table-flow`는 추출·저장·Grid·창 동작의 기존 검토 시안이다. 최근 4개 댓글 반영 이후 **피드백 대기**이며 승인 완료가 아니다.
- 후속 사용자 지시로 순차 수행을 시작한다. 첫 구현은 P02 공용 Grid이며 기존 시안은 그대로 보존한다. 각 공정 상태·보류·재개는 [개별 공정 기록](process/README.md)이 현재 상태의 원장이다.
- HTML 검증은 확장 권한, 실사이트 조작, Native/SQLite, 실제 HWPX 렌더링 검증을 대신하지 않는다. 기존 SQL 공유·IndexedDB 금지 요구는 유지한다.
- 후속 사용자 확정: 앞으로 모델명에 세부 추론 등급을 반드시 함께 표시한다. 각 HTML은 기존 제공 샘플로 채워 실제와 유사한 검토 환경을 구성한다. 이 지시는 샘플 원본 수정이나 실제 사이트 접속·저장을 승인한 의미로 확대하지 않는다.

누적 요구의 원장은 [PRODUCT.md](PRODUCT.md), 확장 정정은 [EXTENSION_REQUIREMENTS.md](EXTENSION_REQUIREMENTS.md), 최근 참고자료 대조와 정정은 [UI_REVIEW_20260929_REFERENCE.md](UI_REVIEW_20260929_REFERENCE.md)다. 이 문서는 구현 공정과 피드백 경계를 소유하며 요구를 새로 축소하지 않는다. 기존 STATUS/UI_REVISION의 검증 기록은 당시 범위의 기록이다.

## 공정 운영 — 설계 제안과 작업 규칙

1. **범위 확인:** 요구 ID, 관련 사용자 정정, 참고 원문 위치, 포함·미연결 기능, 확인할 질문을 해당 공정의 `REVIEW.md`에 작성한다. 충돌은 최신 사용자 답변을 우선하고 임의로 해석하지 않는다.
2. **한 공정 구현:** 사용자가 선택한 기능만 독립 HTML 진입점으로 구현한다. 정적인 모양만 만들고 동작 완료라고 하지 않는다. 입력·상태 변화·실패·취소를 샘플과 테스트 어댑터로 재현한다.
3. **제출 전 검증:** 해당 범위의 알려진 요구와 버그는 제출 전에 수정·검증한다. 범위를 바꾸는 제안은 구현하지 않고 의견으로 분리한다. Playwright 클릭·입력·키보드와 화이트/블랙 캡처를 확인한다.
4. **피드백 대기:** 검토 버전의 파일·증거·변경 목록을 고정한다. 이후 발견한 문제도 우선 기록하고, 사용자 피드백 없이 제출물을 덮어쓰거나 다음 기능을 임의 착수하지 않는다.
5. **지정 부분 수정:** 피드백이 지목한 항목과 그 수정에 직접 필요한 부분만 수정한다. 다른 공정이나 공통 부품에 영향이 있으면 영향 범위를 제시한다.
6. **승인 기록:** 승인한 버전·범위·미연결 항목을 적는다. UI 승인, 기능 시험, 실제 실행 환경 시험을 별도 상태로 관리한다.
7. **조합 검토:** 승인된 공정만 공통 메인에 연결한 새 검토본을 만든다. 개별 승인을 통합본 승인으로 취급하지 않는다. 확장·Gateway·데스크탑 연결은 별도 인수 항목이다.

상태: `범위 대기 → 구현 중 → 검증 중 → 피드백 대기 → 지정 수정 → 사용자 승인 → 조합 검증`. 사용자가 보류를 지시하면 어느 단계에서든 `보류`로 기록하고 지정한 다음 공정으로 이동할 수 있다. 보류 사유·마지막 버전·미해결 항목·재개 조건·의존 공정을 각 공정 파일에 남긴다. 보류는 승인·완료가 아니며 조합 대상에 자동 포함하지 않는다. 뒤 공정의 필요로 승인된 기능을 조용히 변경하지 않는다.

각 독립 진입점은 `prototypes/features/<공정>/index.html`을 제안한다. 기능 JS/CSS·샘플·REVIEW.md·evidence를 같은 폴더에서 소유한다. 아래 파일명은 **예정 경로이며 아직 만들어진 기능이 아니다**. HTML 파일 하나에 코드를 몰아넣으라는 의미가 아니다.

공통 창·테마·Grid는 승인된 부품을 재사용하되, 공통 부품 변경은 별도 버전과 영향 검수로 관리한다. 다른 기능의 상태·테이블을 직접 읽지 않고 기존 공개 계약 및 테스트 어댑터로 연결한다. 검토본의 재현 자료는 사용자 원본을 변경하지 않는다.

## 샘플 환경 — 사용자 확정과 구현 방법

사용자 확정: 기존 샘플 데이터를 채워 실제와 유사하게 확인한다. 빈 화면이나 SAMPLE-001 두 행만으로 업무 기능 검토를 대신하지 않는다.

- 해당 기능과 관련된 `참고자료`의 실제 JSON을 읽어 작업용 복사본으로 사용한다. 현재 table-flow 보고서의 파싱 대상은 31개 JSON·217개 표/화면값 묶음이다. 이는 서로 다른 실제 화면 217개라는 뜻이 아니며 기능별 적합한 자료 선정은 착수 때 확인한다.
- 검토본마다 입력 파일명·해시·선택 화면/표·행/열 수를 기록한다. 보기 좋은 일부 행만 추린 경우 그 범위와 전체 자료 시험 여부를 명시한다.
- 실제 원천 키·키 사전·값 사전·숨김 설정을 가능한 범위에서 함께 적용한다. 숨김 열과 표시명은 원본 행을 삭제하거나 필드를 바꾸지 않는다.
- 접수/공고/계약과 물품, 같은 번호의 다른 차수, 선행 0, 0/false, 소수 단가, 빈값, 중첩 JSON, 중복 표 등 해당 샘플에 존재하는 구조를 유지한다. 자료에 없는 관계를 실제 사실처럼 생성하지 않는다.
- HTML에서는 샘플 화면 문맥과 업무 선택·필터·입력·수정·저장 실패·재열기를 재현한다. 수집·조회·다운로드의 모의 동작은 실제 나라장터 실행과 구분한다. 로컬 테스트용 SQLite 연결 여부도 별도 기록한다.
- 메모/일정/런처/문서 등 제공 샘플이 없는 기능은 해당 자료 유무를 먼저 확인한다. 필요한 최소 예시는 `합성 예시`로 구분하고 실제 업무 샘플과 연결하는 경우 테스트 연결임을 명시한다. 누락된 실제 문서가 검증에 필수면 사용자에게 요청한다.
- HWPX·Excel은 실제 제공 파일이 있는 경우 복사본으로 사용한다. 변환 결과를 다시 열어 확인하며 HTML 표시만으로 파일 생성·레이아웃 보존을 완료 처리하지 않는다.
- 검토 데이터의 기본값을 만드는 작업도 선택된 공정 안에서 수행한다. 기존 피드백 대기 시안을 새 샘플로 조용히 교체하지 않는다.

순서는 기본 제안이다. P02를 먼저 확인하면 추출/DB/취합/사전/관리 화면의 공통 오류를 줄일 수 있다. P01과 선택 기능을 작은 테스트 껍데기로 결합하되 완전한 위젯 구현을 모든 공정의 선행 조건으로 강제하지 않는다. 사용자가 메모 등을 먼저 선택하면 해당 공정부터 진행한다. 기존 1·2·3차 제품 범위는 유지하며, 위 순서가 일정·HWPX 같은 기능 삭제/연기의 새 결정은 아니다.

## 모델 운용과 검토 책임

- 일반 공정 구현: 위 표의 Sol 등급. 명확한 스타일/문구 수정·검토 목록 정리는 Luna medium을 보조로 사용할 수 있으나 수집·저장·HWPX·관계 판단을 맡기지 않는 것을 제안한다.
- 검증: 단순 배치 수정은 Sol high, 자료 보존·동시성·중지·통합 검토는 Sol xhigh. 테스트 수가 많아도 사용자 검토 승인을 대신하지 않는다.
- Astra 필요 판단 시: 해결되지 않은 문제, Sol로 확인한 근거, 요청 등급(복잡한 구조 검토 high, 여러 계층의 난제 xhigh), 기대 산출물을 알린 뒤 **사용자 지시 전 해당 작업 정지**. 임의 호출·자동 전환하지 않는다.
- 현재 작업에서는 모델 전환이나 하위 에이전트 호출을 실행하지 않았다. 현재 모델이 선택 가능한 모델보다 부족/과도하다는 구체적 근거가 있을 때만 변경을 요청한다.
- 작업 시작·검토 제출·전환 요청마다 `모델 ID / 추론 등급 / 담당 공정`을 함께 적는다. 예: `gpt-6-sol / high / P10 메모`. 추천 배정과 실제 실행을 구분한다. 현재 세션의 모델/추론 설정이 확인되지 않으면 추정해 표기하지 않는다. 하위 에이전트를 호출했을 때만 그 호출 설정을 실제 사용값으로 기록한다.
- 멀티에이전트는 승인된 한 공정 안에서 참고자료 대조·구현·검증을 분담하는 경우에 사용한다. 한 명이 해당 기능 코드를 소유하고 검증 담당은 먼저 읽기 전용으로 보고한다. 여러 에이전트가 서로 다른 미승인 기능을 동시에 변경하지 않는다.

근거: [OpenAI 공식 모델 선택 안내](https://developers.openai.com/api/docs/guides/model-selection)를 확인했다. 일반 코딩/검토의 복잡성에 따라 모델과 추론을 선택하고 같은 입력으로 결과를 비교하라는 일반 안내를 PCE에 적용한 배정 제안이다. 정확한 모델 ID와 사용할 수 있는 추론 등급은 이 세션의 앱 도구에 노출된 목록을 기준으로 했다. 가격·할당량은 이번에 비교하지 않았다.
